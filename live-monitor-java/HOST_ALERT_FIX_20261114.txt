主机告警根因与修复报告
时间：2026-11-14，Asia/Shanghai

结论
192.168.195.223 在 00:13:39 收到的“主机资源告警”为错误分类的延迟告警，不是资源指标计算错误，也没有发现当次 CPU、内存、磁盘超过阈值。

生产证据
投递任务：4d1d2538-8491-4ee9-82d8-5cd3e8ca17e0，投递成功。
检测事件：3047244，服务 19，状态 UP。
alert_key：latency_gt_ms:2；response_time_ms：3427。
策略 2：Latency > 3 seconds，阈值 3000 ms，由告警组 2 绑定。
事件 alert_type：NULL，非 host_resource_threshold。
原始指标：CPU 0.3% / 85.0%, Memory 64.1% / 85.0%, Disk 83.0% / 85.0%。
当前磁盘明细也显示 / 为 83%、/boot 为 16%、/home 为 7%；未发现隐藏超限挂载点。

根因
1. 主机 responseTimeMs 是多条 SSH 命令、CPU 采样等待及结果处理的总耗时，不代表主机服务响应时间。confirmLatency 却将通用 3000 ms 延迟规则用于主机资源采集。
2. templateName 只按 serviceType=host 选择资源告警模板，没有区分资源超限、连接异常和采集异常。因为所有资源均未超限，alertItems 为空，最终显示“-”；告警原因回退为原始指标，丢失真实的耗时触发原因。

修复
- 主机采集不再触发通用 latency_gt_ms 策略；其他服务的延迟策略保持原有行为。
- 已存在的主机延迟告警状态在后续检查时归 NORMAL，不发送伪资源恢复通知。
- 资源超限及其恢复仍使用资源模板；主机连接或采集故障使用服务异常模板，保留实际错误信息。
- 未修改 CPU/内存/磁盘阈值，未关闭真实资源告警，未禁用共享告警策略，也未修改历史投递记录。
